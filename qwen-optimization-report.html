所以不是从零移植，主要是把 challenge 中更成熟的细节补进来。

最值得借鉴的优化

1. 输入无关的 shape warm / JIT 预热 —— 优先级最高

challenge 的 Qwen36MTPBlockSession.warmAllDepthShapes() 做得非常彻底：

  • 预热所有合法 verify 宽度：1 ... maxDepth + 1
  • 预热 MTP head 的每个单 token draft step
  • 预热不同 draft 拼接宽度
  • 预热 top-2 / argmax reduction
  • 预热长 KV 上下文的 SDPA
  • 预热 rollback/replay 路径
  • 预热真正运行时使用的 concat 表达式，而不是“看起来相似”的表达式

这对 Python/MLX 版本尤其有价值，因为首次遇到新 shape 时，Metal JIT 编译可能直接落在用户请求延迟中。

建议在 Engine 初始化后增加：

engine.warmup(
    prompt_length=512,
    max_depth=depth,
    kv_lengths=(512, 1024, 2048),
)

并且必须使用与真实 decode 完全相同的调用表达式，例如：

  • mx.concatenate([primary, draft_ids], axis=1)
  • 真实的 eng.forward()
  • 真实的 dr.draft()
  • 真实的 eng.logits()
  • 真实的 rollback 分支

不要只调用一个近似 shape 的 mx.zeros() 运算。

挑战代码中特别强调了：即使 logits warm 过了，只要实际 draftTokenID 或 verify concat 表达式没 warm，第一次计时仍可能产生明显停顿。

2. 让 prefill 只计算最后一个 token 的 logits

challenge 的 begin() 明确避免了对整个 seed 计算 lm_head：

seedLogits = model.callWithHidden(...)
_ = seedLogits
lastLogits = model.applyLMHead(lastHidden)

因为 prefill 期间只有最后一个 hidden 需要投影到 vocab。

已完成（2025-08）：multiplex 新增 Engine.last_logits()，并在普通文本和多模态 prefill 路径中统一使用：

first = int(mx.argmax(eng.last_logits(h)[0, -1]))

该方法在 lm-head 投影前先截取最后一个 hidden，避免产生完整的 [B, L, vocab] logits；旧的全序列路径和 A/B 开关已移除。

固定模型 Qwen3.6-27B-Q4-MTPLX-v2-Q2Mix11-L29UpQ4-Q3KO16 实测（脚本：benchmark_inference.py）：

PromptLegacy prefillOptimized prefill提升
你是什么模型？84.1 tok/s86.8 tok/s1.03x
Python 二叉树前序遍历121.5 tok/s123.5 tok/s1.02x

短 prompt 的端到端 prefill 提升约 2–3%；lm-head 子阶段本身从约 43 ms 降至约 2.3 ms（约 95% 降幅），长 prompt 会获得更明显收益。

3. MTP head persistent history

challenge 中非常重视 MTP head 的历史 KV：

fresh empty head cache → draft 质量较差
persistent head KV cache + committed history → acceptance 明显提高

multiplex 的 Drafter.append_history() 和 Drafter.commit() 已经实现了类似机制：

self.trim_cache_to(cache, self._base + 1)
self.append_history(cache, hidden[:, :m, :], accepted)

但建议进一步核对三个细节：

  1. prefill 的每个 token transition 是否都正确加入 head history；
  2. partial acceptance 时是否只保留 committed prefix；
  3. cache trim 后的位置 offset 是否和 trunk committed length 一致。

尤其是 Scheduler._append_prefill_mtp_history()，这是最容易出现 off-by-one 的地方。challenge 的布局约定是：

head position p = fused(embed(token[p+1]), hidden[p])

建议为 Qwen MTP 增加一个长 prompt + 多轮 partial reject 的 parity 测试。

4. 用 cost model 替代简单的动态 depth

multiplex 当前的 DynamicDepthController 主要基于：

  • full acceptance > 0.8：增加深度
  • full acceptance < 0.5：降低深度
  • cooldown 防止震荡

这是合理的第一版，但 challenge 中使用了更完整的经济模型：

T(d) = verify_cost(d) + d * draft_step_cost
E(tokens | d) = 1 + p1 + p1*p2 + ...

也就是说，最优深度不只由 acceptance 决定，还取决于：

  • MTP head 每步成本
  • verify 宽度变化带来的 kernel 成本
  • rollback 成本
  • 每个位置的条件 acceptance，而不是整体 full acceptance

建议改成记录：

accept_position[i] / trial_position[i]

估计：

p_i = P(draft_i accepted | previous drafts accepted)

然后计算每个候选深度的预期收益：

expected_tokens(d) = 1 + sum(prod(p[:i]) for i in range(1, d + 1))
expected_cost(d) = verify_cost[d] + d * draft_cost
score(d) = expected_tokens(d) / expected_cost(d)

注意

不要直接照搬 challenge 中固定的 cost ratio。它是在特定 M5、特定 Qwen3.8 kernel、特定 head 上测出的。multiplex 应该通过本机 warmup/短基准估计：

  • draft_cost
  • verify_cost[k]
  • partial rollback cost

5. 进一步优化 partial acceptance 的回滚

multiplex 当前已经比普通实现先进：

  • 纯 attention：直接 trim KV
  • hybrid SSM：snapshot + GDN replay
  • rotating KV：重新 replay committed prefix
  • per-row commit：可选 ragged commit

这是 challenge 中最有价值的算法细节之一。

但当前 Engine.snapshot_ssm()：

v + 0

会复制所有 SSM state，可能产生较大的内存和 GPU 开销。

建议借鉴 challenge 的方向：

  • 只保存必要的 recurrent state；
  • 在 forward 中捕获 GDN 中间输入；
  • partial reject 时只 replay GDN，而不是完整 trunk；
  • 对不同 reject depth 建立 shape warm；
  • 对 m == k 的 full acceptance 完全跳过 snapshot/rollback 准备。

当前 scheduler 已经有：

snap = eng.snapshot_ssm(state) if k else None

但可以进一步做到：根据 drafter/模型能力，在确认一定不会 partial rollback 时不创建 snapshot。

6. 真正利用 per-row commit

Scheduler._commit_per_row() 是很有潜力的优化，但当前有明显代价：

eng.extract_row(...)
eng.merge_states(...)

这会把每个 row 拆出来再重新合并，可能抵消收益。

challenge 的设计是单请求 MTP，因此没有 multiplex 的多行对齐问题。对 multiplex 来说建议：

  • B=1：始终使用普通路径；
  • B>1 且 acceptance 差异较小时：继续 take-min；
  • 只有当某行比 batch-min 多接受至少 2 个 token 时，才使用 per-row；
  • 对纯 attention cache 尽量直接 batch trim，而不是 extract/merge；
  • 为 B=2、4、8 分别基准测试。

目前的 MULTIPLEX_PER_ROW_COMMIT=1 应该保持实验性开关，不建议默认开启。

7. MLX allocator / command buffer 管理

challenge 的 RuntimeStartupMemoryPolicy.swift 值得移植其思想：

  • 大内存机器：更大的 allocator cache 和 command buffer
  • 小内存机器：限制 allocator cache，缩短 command buffer
  • warmup 后清理 free buffers
  • 不因为内存小而关闭 compiled decode

multiplex 当前没有看到同等级别的启动策略。建议加入：

mx.set_memory_limit(...)

或通过环境变量设置：

  • allocator cache 上限
  • command buffer referenced-byte 上限
  • warmup 后 mx.clear_cache()

重要原则：

内存 profile 只改变内存管理，不改变推理算法或 kernel 路径。

不要像旧版本 challenge 那样在低内存模式下关闭 compiled decode，否则本地测试路径和生产机器不一致。

8. 长上下文 SDPA 预热

challenge 特别针对：

  • seed 长度 512
  • decode 到 KV 长度 1024
  • qL = 1、2、3、4、5
  • 不同 block/tile family

进行 SDPA warmup。

multiplex 如果主要测试短上下文，容易误以为没有问题；但 coding agent 的上下文经常从 512 增长到几千甚至几万。建议至少预热：

KV length: 512, 1024, 2048
query length: 1, 2, 4, 8
batch: 1, 2, 4

只 warm 与模型实际 attention cache 类型匹配的路径，避免无意义的巨大内存占用。

不建议直接搬过来的东西

1. Challenge 专用 Metal kernel

challenge 中的：

  • NVFP4 quantized matmul
  • MoE gather GEMM
  • Qwen3.8 特化 SDPA
  • Qwen3.8 GDN kernel
  • M5 _nax variant

不能直接用于 multiplex，因为：

  • multiplex 依赖 Python mlx-lm
  • 模型结构可能是 Qwen3.5/3.6、Gemma、其他模型
  • vendored MLX 版本和 challenge 的 Swift MLX fork 不一定一致
  • kernel shape/quantization contract 不同

只有在你准备 fork MLX 并针对单一模型做专用优化时，才值得移植。

2. Wired resident memory

challenge 的 WiredMemoryTicket / resident weights 方案是 M5 专用优化，风险较高：

  • 需要 Swift/Metal API
  • 可能影响系统稳定性
  • 对 Python multiplex 的收益不确定

建议先做普通 allocator 和 warmup，再考虑 wired memory。

3. Challenge 的 benchmark-specific 常数

例如固定的：

  • headStepCostRatio = 0.18
  • 特定 depth price table
  • M5 专用 command buffer 大小
  • 固定 512/1024 shape

不要原样复制，应改为运行时校准或配置项。

推荐实施顺序

第一阶段：低风险

  1. 增加完整 shape/JIT warmup；
  2. 确认 prefill 不计算全序列 lm_head；
  3. 增加长上下文 SDPA warmup；
  4. warmup 后清理 allocator cache；
  5. 为 MTP cache 增加长 prompt / partial reject parity 测试。

第二阶段：中等风险

  1. 将动态 depth 改为 per-position acceptance + cost model；
  2. 优化 SSM snapshot/replay，仅保存必要 state；
  3. benchmark 后再决定是否默认启用 per-row commit；
  4. 对 draft 和 verify 使用异步 eval，尽量重叠 head 与 trunk graph 构建。

第三阶段：高风险

  1. 针对当前主力模型 fork MLX kernel；
  2. 特化 quantized matmul / attention；
  3. 研究 wired resident weights。

总体判断：对 multiplex 最值得借鉴的是 challenge 的“预热 + 精确 rollback + 成本驱动调度”三件套，而不是直接复制 Swift/Metal 代码。
